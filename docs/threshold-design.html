门槛系统 · 设计概览

用户信息体系 + 板块门槛设置的完整方案，聚焦操作便捷性与规则灵活性的平衡。

📋
用户信息分 7 大类
基本、身份、学历、职业、资产、个人状况、专业资质，约 22 个字段，分类填写降低认知负担。
🏅
4 级认证强度
从「自填无需认证」到「人工+活体验证」，每个字段按信息性质设定最高可达等级。
🔒
2 类访问权限
浏览门槛（能看内容）和操作门槛（能发帖/评论/投票），分别独立设置条件组。
⚙️
可视化规则构建
AND/OR 条件组，点击添加/删除，实时预览用户看到的准入说明，无需懂技术。
★ Insight — 核心设计原则
  • 信息填写与认证解耦：用户先填字段值，随时再选择提升认证等级，不强制一次完成
  • 门槛所见即所得：构建规则时实时生成「用户会看到的准入说明」，帮助板块主预判效果
  • 精准引导而非粗暴拒绝：访问受限时告知差哪个条件，并提供一键补全入口
  • 后端实时匹配：访问时对比用户档案与门槛规则，拒绝结果携带每个条件的满足状态

用户信息字段体系

按大类组织，展开每个类别查看字段、认证等级及典型门槛场景。

★ Insight — 认证等级说明
  • 无需认证：纯自填，系统直接信任（如兴趣爱好、语言偏好）
  • 🔵 低级（自填）：用户自填，系统记录但不核实，门槛可要求「至少填写」
  • 🟡 中级（文件）：上传证件，AI 自动 OCR + 逻辑核验，几分钟内出结果
  • 🔴 高级（人工）：上传后人工复核，适合房产证、身份证等敏感证件
  • ⚫ 极高（活体）：人工 + 视频活体验证，最高可信度（可选配置）

用户信息填写体验

分步向导 + 按需认证的两层设计，让用户先完成基础填写，再按需补充认证。

★ Insight — 填写体验原则
  • 渐进式补全：注册时只填基本信息，进入受限板块时才提示补全对应字段
  • 认证与填写分离：字段值和认证等级是独立操作，用户可先填再决定是否认证
  • 明确告知动机：每个字段旁提示「填写后可访问 X 类板块」，提升填写意愿
  • 资料完整度指引：顶部进度条 + 「完善后可解锁 N 个专属板块」激励用户主动补全

资料完整度 45% · 完善后可解锁更多专属板块 🎯

板块门槛设置器

板块管理员设置访问门槛的交互界面原型，支持 AND/OR 逻辑组合多个条件。

★ Insight — 门槛设计要点
  • 两类权限独立设置：浏览门槛和操作门槛可以完全不同，操作门槛通常比浏览门槛更严格
  • 组内 AND，组间 AND/OR：同组内条件全部须满足；多组之间可选「满足任一组」或「全部满足」
  • 实时生成准入说明：设置完毕后自动生成用户侧的准入文本，板块主可直接预览用户会看到什么

用户进入板块的验证体验

用户尝试访问有门槛的板块时，系统如何引导而不是粗暴拒绝。

★ Insight — 拒绝时的体验设计
  • 精确告知差距：「已满足 2/3 个条件，缺少：房产高级认证」而非「您不符合要求」
  • 一键跳转补全：缺哪个字段 / 认证，就显示「去完善」按钮直达对应设置页
  • 区分软拒绝和硬拒绝：软拒绝（信息未填 / 未认证）引导补全；硬拒绝（如年龄不符）才真正拦截

数据结构方案

在现有代码基础上的最小改动方案，重点扩展 SubForum 的门槛字段和新增用户扩展档案表。

★ Insight — 改动最小化原则
  • UserAuthentication 保持不变：继续复用 AuthType + AuthLevel 体系，无破坏性改动
  • 新增 user_profiles 表：存储可选扩展字段，不影响现有 User 表结构
  • SubForum.access_rules 改为 JSON：从简单字符串升级为结构化规则，向后兼容
  • ForumAccessService 新增 checkAccess 方法：拒绝结果携带每条条件的满足状态供前端渲染

          { "field": "property_city", "op": "containsAny", "value": ["上海","北京"], "minAuthLevel": "HIGH"  }

      },
      {

        "rules": [
          { "field": "education",     "op": "gte",        "value": "BACHELOR",       "minAuthLevel": "MEDIUM" }
        ]
      }
    ]
  },
  "action": {
    "groupLogic": "AND",
    "groups": [

👤 新增表：user_profiles（扩展字段，不影响现有 User）
CREATE TABLE user_profiles (
  id              BIGINT       PRIMARY KEY AUTO_INCREMENT,
  user_id         BIGINT       NOT NULL UNIQUE,  -- FK → users.id

  -- 基本
  gender          VARCHAR(10),     -- MALE / FEMALE / OTHER
  birth_year      SMALLINT,        -- 存年份，运行时计算年龄
  nationality     VARCHAR(80),
  city            VARCHAR(80),

  -- 学历
  education       VARCHAR(20),     -- HIGHSCHOOL / BACHELOR / MASTER / PHD
  school          VARCHAR(120),
  major           VARCHAR(120),

  -- 职业
  occupation      VARCHAR(60),
  industry        VARCHAR(60),
  company         VARCHAR(120),
  job_level       VARCHAR(60),

  -- 资产（认证等级另存于 user_authentications）
  property_count  TINYINT,         -- 0 / 1 / 2+
  property_cities TEXT,            -- JSON 数组，如 ["上海","北京"]
  has_vehicle     BOOLEAN,
  income_level    VARCHAR(20),     -- LOW / MEDIUM / HIGH

  -- 个人状况
  marital_status  VARCHAR(20),
  interests       TEXT,            -- JSON 标签数组

  updated_at      DATETIME         NOT NULL
);
⚙️ ForumAccessService 扩展逻辑（伪代码）
public AccessResult checkAccess(Long userId, Long forumId, String action) {
  SubForum     forum    = subForumRepo.findById(forumId)...;
  AccessRules  rules    = JsonSupport.parse(forum.getAccessRules());
  RuleSet      ruleSet  = "view".equals(action) ? rules.view() : rules.action();

  if (ruleSet == null) return AccessResult.ALLOWED;  // 无门槛

  UserProfile              profile    = profileRepo.findByUserId(userId)...;
  Map<ProfileField, AuthLevel> levels = authRepo.getApprovedLevels(userId);

  List<GroupResult> groups = ruleSet.groups().stream()
      .map(g -> evaluateGroup(g, profile, levels)).toList();

  boolean passed = ruleSet.groupLogic() == OR
      ? groups.stream().anyMatch(GroupResult::passed)
      : groups.stream().allMatch(GroupResult::passed);

  return passed
      ? AccessResult.ALLOWED
      : AccessResult.denied(groups);  // 携带每条条件的满足状态 → 前端精准引导
}
